## 0. 结论先行

当前 EFESV3 训练主链路基本接通，但还不能判定为“论文定义意义上的正确接入”。  
最关键的问题不是“完全跑不起来”，而是：

1. inference / prediction 导出链路未真正闭合
2. 低 surprise 时透明透传 base policy 的性质在代码里不成立
3. visited node 的动作语义前后冲突，说明 v3 仍被旧逻辑污染
4. 有几处 shape / mask / 旧框架继承风险，短期不一定爆，但会在实验阶段制造隐蔽偏差

建议按 P0 → P1 → P2 顺序逐项修复。

# P0 严重问题（先修，不然训练/评估结论不可信）

---

## P0-01. inference 链路未闭合

### 现象
EFESV3 的 `rollout()` 已覆盖 train / eval 主流程，但没有和基类 `inference()` 所依赖的数据契约完整对齐。  
父类 inference 需要 `rollout("infer")` 持续写入：

- `self.path_eps`
- `self.inst_ids`
- predictions/prediction file 相关结构

但当前 EFESV3 `rollout()` 只在 `mode == "eval"` 时写 `self.stat_eps` 一类评估信息，没有看到完整 infer 输出链路。

### 涉及文件
- `vlnce_baselines/trainers/train_efes_v3.py`
- 基类：`vlnce_baselines/ss_trainer_ETP.py`

### 风险
- `python run.py --run-type inference` 可能卡住、空输出、输出不完整，或沿用旧逻辑产生不一致结果
- train/eval 看起来正常，但真正导出预测结果时行为不一致
- 论文里若需要 test submission / inference 结果，这条链会直接出问题

### 修复方向
要么：

- 明确补齐 `mode == "infer"` 分支，严格满足基类 inference 契约

要么：

- 重写 EFESV3 自己的 `inference()`，不要再依赖旧父类的隐式数据结构

### 最小回归测试
1. `run.py --run-type inference` 可完整跑完
2. `self.path_eps` 长度随 episode 正常增长
3. 输出结果文件非空，episode id 数量正确
4. 同一 checkpoint 下，eval 和 inference 使用相同的 corrected action 逻辑

---

## P0-02. “低 surprise 时透明透传”在实现中不成立

### 现象
论文/蓝图定义里，Corrector 应满足：

- surprise 低 → gate 接近 0
- gate 接近 0 → `corrected_logits ≈ etp_logits`
- 即：EFES 不应在正常状态下干预 base policy

但当前实现中，`candidate_mask` 不是纯非法候选屏蔽，而是：

- `invalid`
- `visited`

两者合并后的 mask 会在 corrected 路径继续 `masked_fill`。  
更关键的是，即使 `gate == 0`，只要 mask 规则不同，最终输出也已经不再等于原始 ETP logits。

### 涉及文件
- `vlnce_baselines/trainers/train_efes_v3.py`
- `vlnce_baselines/agents/efes_v3_agent.py`

### 风险
- 论文中的“安全性 / 不退化 / transparent pass-through”结论在代码层面不成立
- gate 分布再漂亮，也不等于真的“仅在需要时干预”
- 消融实验会被污染：你以为是在测 Corrector，实际上 mask 本身已经动了 base policy

### 修复方向
必须把两件事彻底拆开：

1. 合法动作屏蔽
   - 只屏蔽 truly invalid candidate
2. EFES 纠偏
   - 只能通过 residual correction / gate 影响 logits
   - 不能把 visited 规则偷偷塞进 corrected path

### 最小回归测试
构造一批样本，使：

- `gate = 0`
- `use_corrector = True`

验证：

- `corrected_logits` 与 base `etp_logits` 在所有合法 candidate 上严格一致

---

## P0-03. visited node 语义前后冲突

### 现象
在动作执行层，旧导航逻辑仍保留：

- `selected_is_visited_node`
- 回到已有图节点 / backtrack 的分支

说明“选择 visited node”本身在环境交互语义里仍是合法动作。  
但上游 EFESV3 的 corrected candidate 打分却先把 visited node 屏蔽掉。

### 涉及文件
- `vlnce_baselines/trainers/train_efes_v3.py`
- 相关旧导航骨架：`vlnce_baselines/ss_trainer_ETP.py`

### 风险
- 动作空间定义不一致
- 训练和执行逻辑之间语义冲突
- 恢复/回退行为被误伤
- “EFES 提升恢复能力”这个主张可能被 mask 逻辑直接破坏

### 修复方向
明确写清楚 v3 的动作语义：

- visited node 到底是不是合法 candidate？
- 如果合法，就不能在上游统一 mask 掉
- 如果非法，就必须同步删掉动作执行层里相关 visited-node 分支

不能同时保留两套互相矛盾的定义。

### 最小回归测试
1. 手工构造一个需要回到 visited node 的 episode
2. 检查 corrected policy 是否真的能选到该类动作
3. 检查 env action 分支与 candidate logits 语义一致

# P1 中等问题（不一定立刻炸，但会影响训练可信度/论文一致性）

---

## P1-01. `d_model` 看似可配，实际上受 ETP 输出维强约束

### 现象
配置里暴露了：

- `EFES_V3.d_model`

看起来像一个普通超参。  
但从数据流看，实际存在隐式 shape 合约：

- `obs_feat` 维度来自冻结 ETP
- `instr_tokens` 维度来自冻结 ETP
- `cand_embeds` 维度来自冻结 ETP
- `TopoBank` 写入的压缩节点特征也和这些维度强相关

这意味着当前实现本质上要求：

- `d_model == ETP hidden dim == language token dim == candidate embed dim`

### 涉及文件
- `run_r2r/efes_v3/efes_v3_main.yaml`
- `vlnce_baselines/trainers/train_efes_v3.py`
- `vlnce_baselines/models/efes_v3/self_state.py`
- `vlnce_baselines/models/efes_v3/predictor.py`

### 风险
- 默认配置下可能没事
- 一旦手改 `d_model`，就会出现：
  - 直接 shape error
  - 或更糟：经过错误投影后悄悄行为异常

### 修复方向
二选一：

1. 把 shape 合约写死
   - 初始化时 assert `d_model == expected hidden dim`
2. 真正补齐投影层
   - 所有来自 ETP 的输入统一投到 v3 内部维度

### 最小回归测试
- 把 `d_model` 改成非 768 后，代码应：
  - 明确报错（如果你选择写死）
  - 或仍可正确跑通（如果你补了投影）

## P1-02. TopoBank attention 可能出现 all-masked row 数值风险

### 现象
`Predictor` 使用 bank attention 时，是按 batch 判断 `has_bank`。  
如果 batch 中只要有一个样本有 bank，就会整批调用 attention。  
这会带来一种边缘情况：

- 某些样本实际上 bank 为空
- 但仍参与这一轮 attention
- 它对应的 key padding mask 可能整行全为 masked

在 mixed precision / 某些 torch 版本里，这种 all-masked attention 行有机会触发 NaN 或非预期输出。

### 涉及文件
- `vlnce_baselines/models/efes_v3/predictor.py`

### 风险
- 训练中后期偶发 NaN
- 难复现
- 只在某些 batch 组合出现，排查成本高

### 修复方向
更稳妥的写法：

- 只对 `has_bank == True` 的样本子集做 attention
- 其余样本直接走零向量 / learnable null memory 分支

### 最小回归测试
构造 batch：

- 一半样本 bank 为空
- 一半样本 bank 非空

在 AMP 下前向多次，确认无 NaN。

## P1-03. `L_cal` 的监督定义与论文表述可能不一致

### 现象
当前 calibration target 更像：

- “base ETP 这一步是否选错”

而不一定是：

- “EFES 输出这一步是否正确”

如果论文中把 `was_this_step_correct` 写成“当前最终动作是否正确”，就与实现不一致。

### 涉及文件
- `vlnce_baselines/trainers/train_efes_v3.py`
- 论文方法节 §3.5

### 风险
- 论文定义与代码实现不匹配
- reviewer 若追问 supervision target，容易暴露不一致
- 分析 surprise/gate 时会误解其语义

### 修复方向
二选一：

1. 修改代码，让 calibration 目标真的是最终 corrected action 的正确性
2. 保留代码，但在论文中准确写明：
   - `L_cal` 学的是 base policy mismatch / anomaly proxy

### 最小回归测试
打印同一 batch 中：

- base argmax 是否正确
- corrected argmax 是否正确
- calibration target 是按哪个定义生成的

确保与论文文字完全一致。

## P1-04. v3 仍然继承自旧 `EFESSelfTrainer`，历史包袱未彻底切断

### 现象
当前 v3 trainer 不是一个干净的新 trainer，而是继续站在旧 self/旧 efes 主线之上继承。  
虽然你已经尽量只用新模块，但仍保留/继承了许多旧结构：

- phase 相关字段
- 旧 trainer 的内部状态管理方式
- 旧 rollout 骨架
- 旧 checkpoint / eval 组织方式

### 涉及文件
- `vlnce_baselines/trainers/train_efes_v3.py`

### 风险
- 今天不一定报错
- 但以后很容易发生：
  - 某个旧字段被误用
  - 某个旧阶段逻辑意外触发
  - 某个旧 eval 假设污染 v3 结果

### 修复方向
中期建议：

- 让 `EFESV3Trainer` 尽量只继承最底层、最中性的 StateNav/ETP trainer
- 不再经过旧 `EFESSelfTrainer` 语义层

### 最小回归测试
- grep / 检查 `train_efes_v3.py` 是否仍依赖旧 self/phase 专属字段
- 移除无关旧字段后确保 train/eval 结果不变

# P2 轻微问题（不改也许能跑，但会影响复现性/可维护性）

---

## P2-01. 启动脚本包含作者机器绝对路径

### 现象
`efes_v3.bash` 中的默认环境变量存在作者本机路径假设，例如：

- `HABITAT_LOCAL_BASE=...`
- `HABITAT_LOCAL_BASELINES=...`

### 涉及文件
- `run_r2r/efes_v3/efes_v3.bash`

### 风险
- 别的机器直接无法复现
- 你过几周换环境后也可能踩坑

### 修复方向
改为：

- 相对路径
- 或显式要求用户传入环境变量
- 或在脚本开头检测路径存在性并报清楚错误

---

## P2-02. 学习率配置命名容易误导

### 现象
配置里同时存在：

- `IL.lr`
- `EFES_V3.lr`

但实际 optimizer 使用的是 `EFES_V3.lr`。  
这很容易让人误以为改 `IL.lr` 也会影响 v3 训练。

### 涉及文件
- `run_r2r/efes_v3/efes_v3_main.yaml`
- `vlnce_baselines/trainers/train_efes_v3.py`

### 风险
- 记录实验时读错超参
- wandb / log / README 中写错学习率来源

### 修复方向
- 明确统一 lr 来源
- 或在日志里打印“实际 optimizer lr 来自 EFES_V3.lr”

---

## P2-03. 配置层级与 logging 字段建议再检查一次

### 现象
从配置结构上看，`EFES_V3.LOGGING` 的缩进/层级值得再人工确认一次。  
如果层级不稳定，可能出现：

- 默认值覆盖异常
- merge 后字段拿不到
- trainer 里取值 silently fallback

### 涉及文件
- `run_r2r/efes_v3/efes_v3_main.yaml`
- `vlnce_baselines/config/default.py`

### 风险
- 日志频率、gate/surprise 统计开关不按预期
- 不一定报错，但行为和你想的不一致

### 修复方向
- 明确核对 YAML 与 `default.py` 的 config node 结构是否完全一致
- 启动时 dump 一份最终 merge 后 config

# 最后判断

如果你把上面 P0 三项修掉，再把 P1-01 / P1-03 做干净，这个 EFESV3 接入才算真正进入“可放心做实验”的阶段。
